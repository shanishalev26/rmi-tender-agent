# סוכנת AI לאיתור וניתוח ראשוני של מכרזי רמ״י

אב־טיפוס לסוכנת שמושכת מכרזים פעילים מרשות מקרקעי ישראל (רמ״י), מורידה את חוברת המכרז, מחלצת ממנה מידע מובנה באמצעות מודל AI, מאתרת את התב״ע הרלוונטית במאגר התכנון, ומדרגת כל מכרז מול פרופיל של חברת נדל״ן — עם הסבר לכל ציון והפרדה ברורה בין מידע שנמשך מהמקור לבין מסקנות המערכת.

## הדגמת המערכת

המאגר כולל 10 רשומות ניתוח סופיות של מכרזים אמיתיים תחת `data/analysis/`. הרשומות לדוגמה מאפשרות להפעיל את ממשק Streamlit ולהציג את תוצאות הצינור בלי להוריד שוב מסמכים או להפעיל מחדש חילוץ AI. תיאור הדגמה והאתגרים המרכזיים שעלו בפיתוח נמצא במסמך [DEMO.md](DEMO.md).

## הוראות הפעלה

### דרישות מקדימות

- Python 3.9 ומעלה (ה-devcontainer משתמש ב-Python 3.11)
- מפתח API של Anthropic

### התקנה

```bash
git clone https://github.com/shanishalev26/rmi-tender-agent.git
cd rmi-tender-agent

python -m venv venv
source venv/bin/activate        # ב-Windows: venv\Scripts\activate

pip install -r requirements.txt
```

### הגדרת מפתח ה-API

המפתח נשמר במשתנה סביבה ולא בקוד. יש ליצור קובץ `.env` בשורש הפרויקט:

```
ANTHROPIC_API_KEY=sk-ant-...
```

בדיקה שהחיבור למודל עובד:

```bash
python test_ai.py
```

### הרצת הצינור המלא

הפקודה הבאה מושכת בעצמה את רשימת המכרזים הפעילים, שומרת אותה ב-`data/tenders.json`, בוחרת את 10 המכרזים הפתוחים הקרובים ביותר לסגירה ומריצה עבורם את כל שלבי העיבוד:

```bash
# פרטים, חוברת, חילוץ AI, חיפוש תב״ע וחישוב התאמה
python build_dataset.py --count 10

# הפעלת הממשק
streamlit run app.py
```

אין צורך להריץ את `fetch_tenders.py` לפני `build_dataset.py`. אפשר להריץ אותו בנפרד רק כדי לרענן את תמונת המכרזים הפעילים בלי להפעיל את יתר הצינור:

```bash
python fetch_tenders.py
```

`build_dataset.py` מדלג על מכרזים שכבר נותחו. כדי להריץ מחדש ניתוח, תכנון והתאמה עבור המכרזים שנבחרו:

```bash
python build_dataset.py --count 10 --refresh
```

### הרצת שלב בודד (לצורכי פיתוח ובדיקה)

את שלבי הניתוח והתכנון אפשר להריץ עצמאית עבור מכרז יחיד; `matching.py` ללא ארגומנטים מחשב מחדש את כל הרשומות:

```bash
python analyze.py 20240085     # פרטי מכרז + הורדת חוברת + חילוץ AI
python planning.py 20240085    # חיפוש התב״ע במאגר התכנון
python matching.py             # חישוב מחדש לכל רשומות הניתוח
```

לחישוב התאמה מחדש עבור קובץ ניתוח יחיד:

```bash
python -c 'from pathlib import Path; from company_profile import load_profile; from matching import calculate_match_for_file; calculate_match_for_file(Path("data/analysis/20240085.json"), load_profile())'
```

## תיאור הארכיטקטורה

המערכת בנויה כצינור עיבוד (pipeline) שבו כל שלב אחראי על תחום אחד בלבד, ומעביר את התוצאה הלאה דרך קובץ JSON מרכזי לכל מכרז. ההפרדה הזו — בין החיבור למאגרים, חילוץ המסמכים ולוגיקת ההתאמה — מאפשרת להריץ, לבדוק ולהחליף כל שלב בנפרד.

```
build_dataset.py        משיכת המכרזים הפעילים, בחירת הקרובים לסגירה
        │                והרצת הצינור על כל אחד
        ├── fetch_tenders.py   SearchApi → data/tenders.json
        ├──► analyze.py         פרטי המכרז + הורדת חוברת + חילוץ AI
        │        ├── get_booklet.py   נרמול נתוני רמ״י, מסמכים והורדת PDF
        │        └── extract.py       חילוץ שדות מהחוברת באמצעות Claude
        │
        ├──► planning.py        חיפוש התב״ע במאגר התכנון ובחירת התכנית
        │
        └──► matching.py        חישוב ציון ההתאמה לפרופיל החברה

rmi_client.py          session משותף מול MichrazimSite
analysis_store.py      טעינה ושמירה אטומית של רשומות ניתוח
company_profile.py     טעינה, אימות ושמירת פרופיל החברה
app.py                 ממשק Streamlit להצגת התוצאות ולעריכת הפרופיל
```

### עקרון מנחה: הפרדת מקורות

לכל מכרז נשמרת רשומה אחת תחת `data/analysis/<michraz_id>.json`, שבה כל מקור מידע יושב בשדה נפרד תחת `sources` — `rmi_api`, `tender_booklet_ai`, `planning_api` — ולכל אחד סטטוס משלו. המסקנות של המערכת (ציון ההתאמה) נשמרות בנפרד תחת `derived_analysis`. כך תמיד ברור מאיפה הגיע כל נתון, והאם הוא עובדה מהמקור או מסקנה של המערכת.

## מקורות המידע ואופן החיבור

המערכת משתמשת בשני מקורות נתונים ציבוריים של רמ״י — אתר המכרזים ואתר התכניות — וב-Anthropic Claude כשירות חיצוני לחילוץ מידע מחוברות. Claude אינו מקור מידע של רמ״י: הוא מעבד רק את ה-PDF שנמסר לו.

### 1. מאגר מכרזי רמ״י

- **עמוד המקור:** `apps.land.gov.il/MichrazimSite`
- **רשימת המכרזים:** `POST /api/SearchApi/Search` — מוחזרים המכרזים הפעילים.
- **פרטי מכרז:** `GET /api/MichrazDetailsApi/Get` — ה-JSON הגולמי המלא של מכרז בודד, שנשמר במלואו.
- **הורדת מסמכים:** `POST /api/MichrazDetailsApi/GetFileContent` — הורדת חוברת המכרז.
- **טבלאות קוד:** `GeneralTablesApi` ו-`YeshuvimApi` — לתרגום סוג מכרז, יישוב וייעוד. ייעוד המכרז והקטגוריה הרשמית שלו מגיעים מאותן שורות `TableID = -1`.

חוברת המכרז מזוהה לפי המסמך שתיאורו "חוברת המכרז" ברשימת המסמכים. כאשר לא נמצאת חוברת, הדבר מסומן מפורשות (`processing_status: not_found`) והצינור ממשיך בלעדיה.

### 2. מאגר התכניות (תב״ע)

- **עמוד המקור:** `apps.land.gov.il/TabaSearch`
- **חיפוש תכניות:** `POST /api/SerachPlans/GetPlans` — לפי מספר תכנית או גוש/חלקה.
- **פרטי תכנית:** `GET /api/Plan/GetPlanData` — לשליפת הייעוד המרכזי, יחידות הדיור ומסמכי התכנית עבור התכנית שנבחרה.

### שירות חילוץ AI

- **ספק:** Anthropic (Claude), דרך ה-SDK הרשמי `anthropic`.
- **חיבור:** מפתח ה-API נטען מ-`.env` דרך `python-dotenv`, ולעולם אינו נשמר בקוד.

## אופן השימוש במודל ה-AI

מודל ה-AI משמש למשימה אחת וממוקדת: חילוץ מידע מובנה מתוך חוברת מכרז — מסמך PDF ארוך בעברית שהמבנה שלו משתנה ממכרז למכרז.

- **המודל:** `claude-sonnet-5`.
- **הקלט:** קובץ ה-PDF של החוברת נשלח ישירות למודל (מקודד ב-base64), יחד עם הנחיה מובנית.
- **הפלט:** JSON בלבד, עם ארבעה שדות — `plan_number`, `land_designation`, `threshold_conditions` ו-`point_to_check`.

עקרונות שנבנו לתוך ההנחיה כדי לשמור על אמינות:

- **בלי המצאות.** המודל מונחה להשתמש אך ורק במידע שמופיע בחוברת, ולא להשלים ממקורות חיצוניים.
- **מקור לכל נתון.** לכל שדה שחולץ המודל מחזיר את מסמך המקור, מספר העמוד, ציטוט מילולי מדויק מהחוברת, ורמת ביטחון (`high` / `medium` / `low`).
- **הבחנה מפורשת בין מושגים.** ההנחיה כוללת כללים למניעת בלבול נפוץ — למשל בין מספר תכנית לבין מספר גוש, חלקה, מגרש או היתר; ובין תוקף ערבות לבין סכום ערבות.
- **סימון מפורש של מידע חסר.** כאשר נתון אינו מופיע בבירור, המודל מחזיר `value: null` עם `confidence: low` במקום לנחש.
- **ייעוד קרקע מפורש בלבד.** `land_designation` מתקבל רק כאשר ייעוד הקרקע או השימוש בה נאמר במפורש בחוברת. אין להסיק אותו ממטרת או מסוג המכרז, מייעוד המכרז ברמ״י, מהיישוב, ממספר התכנית או מתיאור המגרש.

ה-AI מחלץ ראיות מתוך החוברת ואינו מחליף נתונים מובנים שמתקבלים מרמ״י. כאשר קיים מספר תכנית שימושי גם מרמ״י וגם מחילוץ החוברת, שני המקורות נשמרים ומשמשים את שלב התכנון. מספר התכנית שחולץ נבדק לפני חיפוש מול ערכי גוש, חלקה ומגרש ידועים כדי להימנע משימוש בערך שאינו מספר תכנית. `land_designation` נשמר ברשומת הניתוח עם provenance מלא, אך כיום אין לו שורת תצוגה ייעודית בממשק.

## איתור התכנית

`planning.py` שומר את הפניות הגולמיות מרמ״י, אך שולח לחיפוש אוטומטי רק הפניה לא ריקה שמכילה לפחות ספרה. כך ערכים כלליים כמו `תמל`, `תכנית` או `תב״ע` אינם יוצרים חיפוש רחב ולא מדויק.

ראיות מספר התכנית נבנות מכל ההפניות השימושיות של רמ״י ובנוסף ממספר שימושי שחולץ מהחוברת, ללא כפילויות וללא השלכת מקור אחד כשהאחר קיים. ערך AI שזהה לגוש, חלקה או מגרש ידועים אינו משמש כמספר תכנית. כאשר קיימים גוש וחלקה, מתבצע גם חיפוש קדסטרי.

התוצאות מאוחדות ומדורגות לפי התאמה מדויקת למספר תכנית ולפי מילות מיקום/כתובת מנתוני המכרז, ונשמרים הסיבות לציון, payload החיפוש ומספר התוצאות. בחירה אוטומטית נעשית רק כאשר יש מועמדת בעלת ציון חיובי וגבוה באופן יחיד. תיקו בציון הגבוה או מועמדות ללא ראיה חיובית אינם מוכרעים לפי סדר ה-API.

הנתונים והממשק מבחינים בין תכנית שנבחרה, מספר מועמדות שלא ניתן להכריע ביניהן, מספר תכנית ידוע שלא נמצא לו מענה ב-TabaSearch, והיעדר ראיות מספיקות לחיפוש.

## מנגנון ההתאמה

לכל מכרז מחושב ציון התאמה בין 0 ל-100 מול פרופיל החברה, לפי שישה קריטריונים עם משקלים מפורשים (`matching.py`):

<table dir="rtl">
  <thead>
    <tr><th>קריטריון</th><th>משקל</th></tr>
  </thead>
  <tbody>
    <tr><td>אזור פעילות</td><td>20</td></tr>
    <tr><td>סוג פרויקט</td><td>20</td></tr>
    <tr><td>מספר יחידות דיור</td><td>20</td></tr>
    <tr><td>הוצאות פיתוח</td><td>15</td></tr>
    <tr><td>סטטוס תכנוני (תכנית מאושרת)</td><td>15</td></tr>
    <tr><td>זמן עד להגשה</td><td>10</td></tr>
  </tbody>
</table>

לכל קריטריון אחד מארבעה סטטוסים:

- **מתאים** (`matched`) — המידע ידוע ועומד בדרישה.
- **לא מתאים** (`not_matched`) — המידע ידוע ואינו עומד בדרישה.
- **דורש בירור** (`needs_clarification`) — הקריטריון חל, אך המידע אינו מספיק להכרעה.
- **לא רלוונטי** (`not_applicable`) — הקריטריון אינו חל על המכרז.

### חישוב שקוף ונקי מהטיה

המשקלים המוגדרים מסתכמים ב-100, אך הציון מנורמל לפי הקריטריונים שחלים בפועל על המכרז. קריטריון `not_applicable` שומר את משקלו ברשומת הקריטריון ומקבל 0 נקודות גולמיות, אך אינו נכלל במכנה של הציון, של `known_match_score` או של `data_coverage`, ואינו מסומן כמידע חסר.

קריטריון `needs_clarification` נשאר קריטריון חל ומקבל קרדיט חלקי של 20% ממשקלו (`MISSING_DATA_CREDIT`). לכן הוא נכלל בציון הסופי, אך לא במדדים המבוססים רק על הכרעה ידועה.

```text
applicable_weight = סכום משקלי הקריטריונים שאינם not_applicable
applicable_points = סכום הנקודות של הקריטריונים החלים
score = applicable_points / applicable_weight × 100

known_match_score = הנקודות מקריטריוני matched ו-not_matched
                    / המשקל שלהם × 100

data_coverage = משקל קריטריוני matched ו-not_matched
                / applicable_weight × 100
```

כאשר מכנה רלוונטי הוא 0, הקוד מחזיר 0 ונמנע מחלוקה באפס. כל שלושת המדדים מעוגלים באותו אופן שבו הם נשמרים ברשומת הניתוח.

ערך מספרי `0` הוא מידע ידוע ולא מידע חסר; ערך בוליאני אינו נחשב מספר. יחידות דיור הן קריטריון חל כאשר הקטגוריה הרשמית של ייעוד המכרז היא `מגורים`, אינן חלות כאשר הקטגוריה היא `אחר`, ובקטגוריה חסרה או לא מוכרת נדרש בירור. ההחלטה אינה מבוססת על מספר יחידות הדיור עצמו.

בהשוואת סוג הפרויקט, קטגוריית רמ״י הרשמית `מגורים` יכולה לשמש כערך ההשוואה מול פרופיל החברה, בעוד שהייעוד הספציפי — למשל תת-סוג רשמי — נשמר כערך המוצג בפועל. אין תנאים מיוחדים לייעוד או למכרז מסוים.

### מהציון להמלצה

- כיסוי מידע נמוך מ-40% → **דורש בירור** (ללא קשר לציון)
- ציון 80 ומעלה → **התאמה גבוהה**
- ציון 60–79 → **מתאים לבדיקה**
- ציון 40–59 → **דורש בירור**
- ציון מתחת ל-40 → **התאמה נמוכה**

לכל קריטריון נשמר הסבר מילולי (הערך בפועל, הערך הנדרש, והסיבה לסטטוס), והמשקלים מוגדרים במקום אחד (`WEIGHTS`) כך שניתן לשנותם בקלות. פרופיל החברה נערך דרך טופס בממשק, ושמירתו מפעילה חישוב מחדש של ההתאמה לכל המכרזים.

## מבנה הנתונים

כל הנתונים נשמרים תחת `data/`:

```
data/
├── tenders.json              תמונה עקובה של המכרזים הפעילים מרמ״י
├── company_profile.json      פרופיל החברה
├── analysis/<id>.json        10 רשומות ניתוח סופיות לדוגמה, עקובות ב-Git
├── details/<id>.json         JSON גולמי שנוצר בזמן ריצה ומוחרג מ-Git
└── booklets/<id>.pdf         PDF שמורד בזמן ריצה ומוחרג מ-Git
```

`data/tenders.json` ורשומות הדוגמה תחת `data/analysis/` נשמרים במאגר. לעומתם, `data/details/` ו-`data/booklets/` הם תוצרי ריצה שניתנים לשחזור ולכן מוגדרים ב-`.gitignore`. קובצי הדוגמה מאפשרים להציג את המערכת בלי לחזור על הורדות ועל קריאות בתשלום ל-Claude. רשומות הניתוח נשמרות באופן אטומי דרך `analysis_store.py` כדי לא להשאיר JSON חלקי.

הרשומה המאוחדת (`analysis/<id>.json`) בנויה כך:

```
{
  "michraz_id": ...,
  "analyzed_at": ...,
  "documents": [ ... ],          # מטא-דאטה של המסמכים שהורדו
  "sources": {
    "rmi_api":            { "status": ..., "data": ... },   # עובדות מרמ״י
    "tender_booklet_ai":  { "status": ..., "data": ... },   # חילוץ ה-AI
    "planning_api":       { "status": ..., "data": ... }    # תוצאות התב״ע
  },
  "derived_analysis": {
    "company_match": { ... }     # מסקנת המערכת — ציון ההתאמה
  }
}
```

## מגבלות שזוהו

- **תלות ב-API פנימי.** החיבור מסתמך על endpoints לא מתועדים של MichrazimSite ושל TabaSearch, שעלולים להשתנות או להיות בלתי זמינים ללא התראה.
- **כיסוי ופורמט במאגר התכנון.** מספר תכנית ידוע עשוי לא להחזיר תוצאה ב-TabaSearch. המערכת מסננת הפניות כלליות חסרות ספרות, אך אינה משכתבת באופן רחב פורמטים שונים של מספרי תכנית.
- **בחירת תב״ע שמרנית.** תיקו בציון הגבוה, ציון אפס או היעדר תוצאות אינם מוכרעים לפי סדר ה-API. פרטי תכנית ומסמכיה המלאים נטענים רק לאחר בחירה אמינה.
- **חילוץ AI תלוי בחוברת.** כאשר אין חוברת או שהמידע אינו נאמר במפורש, השדה נשאר חסר במקום להיות מושלם בהשערה.
- **פער תצוגה מצומצם.** `land_designation` מחולץ ונשמר, אך עדיין אינו מוצג בשורת UI ייעודית. אין שדה רשמי נפרד ל"שם מכרז", ולכן הממשק אינו ממציא אחד.
- **התאמת טקסט בסיסית.** השוואת אזורי פעילות וסוגי פרויקטים מבוססת על נרמול והכלת מחרוזות, ולא על מיפוי סמנטי מלא של שמות יישובים או ייעודים.
- **ללא מקביליות.** המכרזים מעובדים בזה אחר זה. עיבוד היקף גדול יידרש לתזמון ולעבודה במקביל.

## הצעות להמשך

- **זיהוי שינויים.** סימון מכרזים חדשים מאז הסריקה האחרונה, ושינויים במועד ההגשה או בגרסת החוברת.
- **חילוץ ותצוגה מעמיקים יותר.** הצגת `land_designation` בממשק, שליפת מידע נוסף מתקנון התב״ע והשוואת נתוני החוברת לנתוני התכנית.
- **נרמול תכניות מבוקר.** תמיכה גנרית בווריאציות כתיב של מספרי תכנית או מקור תכנוני נוסף, בלי ליצור התאמות רחבות מדי.
- **תיקון ידני.** אפשרות לערוך נתון שחולץ באופן שגוי, ולתעד את התיקון.
- **תמיכה במספר פרופילים.** ניהול כמה פרופילי חברה במקביל והשוואת דירוג ביניהם.
- **מפה.** הצגת המכרז והתכנית על מפה לפי הגוש והחלקה.
- **סיכום מנהלים ורשימת שאלות.** יצירה אוטומטית של סיכום קצר לכל מכרז ורשימת שאלות ממוקדות לאדריכל, שמאי או עורך דין.
- **התראות.** התראה על מכרז חדש בעל התאמה גבוהה לפרופיל.
